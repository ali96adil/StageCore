# **1. الملخص التنفيذي**

StageCore هو منصة مركزية لإدارة وتشغيل العروض الحية والمسرحية والفعاليات والبروفات وأنظمة Live Production. يجمع النظام الـCues، الأجهزة، الـInputs والـOutputs، الـRouting، الملاحظات، البروفات، الأتمتة، السكربتات، الـPlugins، والـStageCore Nodes ضمن مشروع واحد يفهم العرض ككيان مترابط.

لا تتمثل قيمة StageCore في كونه زر GO أو Cue Player جديدًا؛ بل في كونه طبقة **Show Logic + Control + Integration + Memory** فوق البرامج والأجهزة المتخصصة. فهو يعرف ما الذي حدث، وما الذي يحدث الآن، وما المتوقع لاحقًا، وما الأجهزة المسؤولة، وما الذي تعلمه الفريق خلال البروفات. وبذلك يحول بيئة التشغيل من مجموعة أدوات منفصلة وملاحظات ورقية إلى نظام موحد قابل للتوثيق والتكرار والتحقق.

| **تعريف المنتج:** StageCore هو العقل المركزي للعرض، لا البديل الكامل عن كل برنامج متخصص. يبدأ كمنصة Cue + Device + Rehearsal Management، ثم يتطور إلى Live Show Control Platform، ثم إلى Distributed Show Control System. |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

يعتمد الإصدار v0.2 على مبادئ ثابتة: Local First، Project Based، Plugin First، Capability Based، Event Driven، Hardware Independent، وفصل مسار التحكم الحرج عن المعالجة الثقيلة. ويضيف إلى رؤية v0.1 محرك Universal I/O Routing، عائلة Nodes موزعة، فصل الهوية الفيزيائية للجهاز عن اسمه داخل المشروع، استراتيجية واضحة للزمن الحقيقي، وShow Memory System أكثر نضجًا.

## **1.1 غرض هذه الوثيقة**

هذه الوثيقة هي مرجع رؤية المنتج والقرارات المعمارية واتجاه التطوير. وهي ليست Implementation Specification أو API Contract نهائيًا؛ بل تحدد ما يجب أن يبقى صحيحًا عند تحويل الرؤية لاحقًا إلى متطلبات، نماذج بيانات، تصميم واجهات، وخطط تنفيذ.

## **1.2 قاموس النطاق والنضج**

| **التصنيف**           | **المعنى في هذه الوثيقة**                                                                                                |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------|
| Core                  | مبدأ أو قدرة أساسية تشكل هوية النظام ويجب أن توجه التصميم منذ البداية. لا يعني بالضرورة اكتمال كل تفاصيلها في أول إصدار. |
| MVP                   | الحد الأدنى القابل للبناء والاختبار الذي يثبت القيمة المركزية للمنتج.                                                    |
| Post-MVP              | قدرة مهمة بعد إثبات الأساس، لكنها ليست شرطًا لأول نسخة قابلة للاستخدام.                                                   |
| Future / Experimental | اتجاه توسعي أو بحثي لا ينبغي أن يعقد النواة أو المسار الحرج الآن.                                                        |

## **1.3 النتيجة المستهدفة**

يصل StageCore إلى نقطة يستطيع فيها Technical Director اختيار **Load Show**، فيحمّل النظام الأجهزة والـRouting والـCues والملاحظات والـPlugins وبيانات البروفات، ثم ينفذ Pre-Show Check ويعرض **SHOW READY** أو قائمة مشكلات واضحة قبل فتح العرض للجمهور.

# **2. رؤية المنتج وحدوده**

## **2.1 الرؤية**

الرؤية هي بناء منصة تستطيع أن تكون العقل المركزي للعرض. عند فتح Project، يجب أن يعرف StageCore:

- معلومات العرض والموقع والفريق والنسخة الحالية.
- الأجهزة والبرامج والخدمات المرتبطة، وحالتها وطرق الاتصال بها.
- الـInputs والـOutputs ومجموعاتها وأسماؤها المنطقية داخل المشروع.
- الشاشات والبروجكترات والكاميرات والصوت والإضاءة والطباعة وBarcode/RFID والسنسورات.
- بنية Act → Scene → Cue → Actions وترتيب الـCues واعتمادياتها.
- Current Cue وNext Cue وPrevious Cue وما يجب أن يحدث في كل منها.
- ما حدث في البروفات والعروض السابقة: توقيت، انتقالات، أخطاء، Overrides وملاحظات.
- ما يمكن اقتراحه للمشغل دون انتزاع القرار النهائي منه.

## **2.2 المشكلة التي يحلها**

تتكون بيئة العرض عادة من برامج Video Playback، Lighting Consoles، Audio Systems، Switchers، Scripts، Controllers، Projectors، Printers، Nodes، جداول، وCue Sheets ورقية. كل عنصر يملك جزءًا من الحقيقة، بينما يبقى منطق العرض موزعًا بين ذاكرة الفريق وأدوات غير مترابطة. StageCore يوحد **منطق العرض وحالته وذاكرته** ويترك التنفيذ المتخصص للأدوات الأنسب.

## **2.3 ما ليس StageCore في البداية**

لن يحاول StageCore في MVP أن يصبح:

- Video Playback Engine كاملًا بدل Resolume أو QLab أو Media Servers.
- Lighting Console كاملًا.
- Audio DAW كاملًا.
- Video Switcher كاملًا.
- بديلًا مباشرًا لطبقات الأمان المعتمدة للـPyro أو Motors أو Emergency Systems.

يمكن إضافة Engines أصلية لاحقًا إذا ثبتت حاجة حقيقية، لكن الأولوية تبقى للتكامل والتحكم والذاكرة. المسار المعتاد للبروجكتر، مثلًا، يبقى **Mac / Media Server → HDMI أو SDI → Projector**، بينما ينفذ StageCore التحكم الشبكي والحالة عبر PJLink أو Plugin مناسب.

## **2.4 هوية المنتج**

الاسم هو **StageCore**، والعبارة المرجعية المقترحة:

| **StageCore — The Operating System for Live Shows** |
|-----------------------------------------------------|

بدائل تسويقية ممكنة: **Run the Show. Control Everything.** أو **One Core. Every Cue.** لكن تعريف Operating System هو الأكثر اتساقًا مع دور طبقة التنظيم والتكامل والذاكرة.

# **3. مبادئ التصميم**

## **3.1 Show First**

يفكر المستخدم في العرض والـCue والنتيجة المرئية أو السمعية، لا في البروتوكولات أولًا. يجب أن تخفي الواجهة التعقيد عندما لا يكون مطلوبًا، وتسمح بالوصول إليه عندما يحتاجه المستخدم المتقدم.

## **3.2 Project Based**

كل عرض Project مستقل، مثل: العميان، Macbeth، Opening Ceremony، أو Concert 2027. يحتفظ المشروع بإعداداته وأسماء أجهزته المنطقية وCue List وMedia وNotes وRouting وRehearsal History، دون إعادة تكوين المنصة بالكامل عند الانتقال إلى عرض آخر.

## **3.3 Local First**

يجب أن يستمر Live Show دون إنترنت. يمكن استخدام الإنترنت للمزامنة والنسخ الاحتياطي والتحديثات والخدمات المستقبلية، لكنه ليس اعتمادًا في مسار GO أو STOP أو تنفيذ الـCue. البيانات التشغيلية الأساسية محفوظة محليًا، ويمكن تشغيل Stage Network مستقل.

## **3.4 الاستقلال عن العتاد ونموذج القدرات**

لا يرتبط StageCore بشركة أو موديل. يتعامل مع قدرات معلنة مثل power, select_input, send_osc, relay_set, أو print_qr بدل افتراض أسماء أجهزة ثابتة. توفر الـPlugins ترجمة هذه القدرات إلى بروتوكولات وأوامر فعلية.

## **3.5 Plugin First مع نواة صغيرة**

تحتفظ النواة بإدارة المشروع والحالة والـCue والـRouting والأحداث والسلامة والبيانات. تأتي التعريفات والبروتوكولات وDrivers وUI Panels والتكاملات المتغيرة عبر Plugins/Extensions. لا ينبغي أن يتحول كل تكامل جديد إلى تعديل داخل Core.

## **3.6 Event Driven**

تتواصل مكونات النظام عبر Event Bus بعقود واضحة. أمثلة: cue.started, cue.completed, device.connected, device.disconnected, route.triggered, note.created, barcode.scanned, وrehearsal.started. يسمح ذلك بالفصل بين الطبقات وإضافة Plugins وLogs وAutomation دون تشابك مباشر.

## **3.7 Rehearsal Driven**

البروفة مصدر بيانات وليست مجرد تشغيل تجريبي. يسجل StageCore التنفيذ الفعلي والتوقيت والانتقالات والتعديلات والأخطاء والملاحظات، ثم يحولها إلى Show Memory تساعد الفريق على التحسين والاستعداد.

## **3.8 Safety by Design**

ليست كل الأفعال متساوية. يجب التفريق بين Normal وCritical وSafety-Critical Actions، مع صلاحيات وConfirmations وInterlocks وFail-safe States مناسبة. StageCore لا يختصر أنظمة الأمان المادية أو الاعتمادات المطلوبة.

## **3.9 Progressive Complexity**

يقدم Simple Mode إعدادًا بصيغة WHEN / DO، بينما يسمح Advanced Mode بـVisual Routing Graph وتفاصيل أعمق. لا يُجبر المستخدم على فهم البروتوكول الداخلي أو الرسم البياني كي ينشئ عملية بسيطة.

## **3.10 Reliability over Novelty**

في بيئة Live، الاستقرار والحتمية والوضوح أهم من كثرة الميزات. أي Feature لا تجعل التشغيل أكثر تنظيمًا أو أمانًا أو سرعة أو قابلية للتكرار ليست أولوية.
