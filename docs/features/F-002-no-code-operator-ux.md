# F-002 — No-code / Low-code Operator UX

**Status:** Cross-cutting product contract; implementation begins with the Operator Web foundation slice and continues across every later StageCore feature.

## Product rule

StageCore must expose a simple visual path for every common operator workflow. Raw JSON, protocol addresses, scripts, shell commands, database editing, IDs and implementation-specific terminology are expert details, not the normal user experience.

F-002 is not a single screen. It is the interaction contract for the entire product.

## Relationship to Arabic UI

F-002 defines language-neutral user journeys, information architecture, progressive disclosure and no-code controls.

F-001 owns localization architecture, Arabic translation and RTL presentation. F-002 must be localization-ready and RTL-safe so F-001 can translate the same workflows without redesigning them.

The Arabic UI must translate the complete operator experience, including labels, statuses, validation, errors, help text, confirmation prompts and guided steps. Internal API/event/engineering identifiers remain stable English contracts and must not be translated in storage or wire protocols.

## Design principles

1. **Goal first, implementation second.** Start with what the operator wants to do: prepare, rehearse, run, inspect or fix.
2. **One obvious primary action.** Each state should have a clear recommended next step.
3. **Progressive disclosure.** Common controls are visible. Expert controls live under an explicit Advanced section.
4. **Never require code for the common path.** JSON, OSC argument objects, schemas and policy documents are generated by visual builders where a supported model exists.
5. **Capability aware.** Do not display fake controls for capabilities that are not actually available. Future features may have reserved UX locations in documentation, but the live product only offers working actions.
6. **Explain consequences before mutation.** Publish, enter SHOW, exit SHOW, destructive edits, repair/update and recovery flows must state what changes and what remains unchanged.
7. **Safety state is always visible.** SHOW/REHEARSAL/SIMULATION, configuration lock, readiness, active Session, current Cue and next Cue must never be hidden behind expert views.
8. **Human names first.** Display Project, Cue, device/profile and Session names first; IDs are copyable expert metadata.
9. **Errors must be actionable.** Prefer “Projector is reachable but OSC port 9000 did not respond” over a raw error code. Preserve the code in details for support.
10. **No modal mazes.** Multi-step work should use a guided flow with visible progress and a safe way back.
11. **Touch friendly.** Primary runtime controls must remain usable on tablets and stage touchscreens without relying on hover or tiny targets.
12. **Keyboard friendly.** Desktop operator workflows must support predictable focus, shortcuts and confirmation semantics without sacrificing safety.
13. **Critical path isolation.** UX enrichment must not add latency or blocking work to GO/P0/P1 runtime execution.

## Product information architecture

The long-term operator experience is organized by goals instead of backend modules.

### Projects

- create/open/import a show;
- recent and pinned Projects;
- readiness summary;
- last Session and quick resume/rehearsal entry when truthful state allows it.

### Project Home

A project-specific command center showing:

- current mode and configuration-lock state;
- current published Snapshot and Draft state;
- readiness blockers/warnings;
- current/next Cue when a Session is active;
- recommended next action;
- quick paths to Setup, Cues, Run and Review.

### Setup

Guided configuration for:

- devices/targets;
- inputs/triggers;
- outputs/actions;
- routing/mappings;
- media and execution environment requirements;
- profiles/plugins when those features exist;
- advanced raw configuration only as an optional expert section.

### Cues

- visual Cue list and ordering;
- create/edit/duplicate/enable/disable without raw JSON;
- action builder using capability-aware controls;
- advanced policy/parameter JSON only when a visual editor does not yet cover an expert case;
- validation and publish workflow with understandable blockers.

### Check / Preflight

- readiness result grouped as Blocker / Warning / Advisory / Ready;
- grouped by device, media, network, permissions, plugin and environment when those signals exist;
- each finding provides “what happened”, “why it matters” and “what can I do now?”;
- test/fix/retry actions when safe and supported.

### Run

A theatre-first live workspace:

- obvious mode banner;
- current Cue, next Cue and active Session;
- large GO control with explicit command/result feedback;
- start rehearsal / enter SHOW / exit SHOW as guided actions;
- STOP only where runtime semantics support it;
- no configuration mutation controls while SHOW lock is active;
- timing intelligence appears as advisory context, never autonomous GO.

### Review

- Sessions and rehearsal/show history;
- notes;
- timing observations and later F-028 analytics;
- Cue/action outcomes and errors;
- export/report actions when those features exist.

### System

As later features land:

- devices and discovery;
- plugins/add-ons;
- diagnostics/Doctor;
- network cockpit;
- updates/backups;
- appearance/language/workspace preferences;
- expert and developer tools.

## Guided lifecycle

For a normal new Project, the default journey is:

1. Create Project.
2. Connect or define devices/targets.
3. Build Cues visually.
4. Validate.
5. Publish a Runtime Snapshot.
6. Run Preflight.
7. Rehearse.
8. Enter SHOW when ready.
9. Run the show.
10. Exit SHOW.
11. Review the Session and notes.

StageCore may skip steps that are not needed for a particular Project, but it must not force an operator to understand revisions, UUIDs or storage internals to advance.

## Basic and Advanced modes

Every supported editor follows this rule:

- **Basic** is the default and must be enough for common workflows.
- **Advanced** exposes implementation-level configuration only when useful.
- Switching to Advanced never changes runtime state by itself.
- Advanced data must round-trip without being silently discarded by the Basic editor.
- A Basic editor must never pretend it understands an advanced structure it cannot safely preserve.

## First foundation slice

The first F-002 slice establishes:

- a guided Project Home with a visible lifecycle and recommended next actions;
- simpler goal-oriented navigation labels;
- a reusable Basic/Advanced disclosure pattern;
- a visual OSC target builder that generates the existing target configuration contract;
- a visual OSC action builder for address and common argument types while retaining full JSON in Advanced;
- preservation of existing authenticated APIs, RBAC, immutable Runtime Snapshots and SHOW configuration lock;
- explicit localization/RTL hooks for F-001 rather than hard-coding future layout assumptions.

## Later F-002 slices

F-002 remains open and is applied to later capabilities as they become real:

- visual trigger/condition/transform builder;
- schemas generated from device/profile capabilities;
- guided Preflight remediation;
- Session start/resume workflows from F-027;
- timing intelligence presentation from F-028;
- installer/setup/discovery/profile/plugin/update flows;
- Android/tablet and Stage Display controls;
- timecode mapping;
- show capsule/export/import;
- simulation/recovery;
- specialist visual-engine workflows;
- optional assistant-generated drafts with operator review.

## Explicit non-goals

- Do not translate persisted API/event keys as part of F-002.
- Do not invent runtime capabilities that do not exist.
- Do not hide safety state to make the UI look simpler.
- Do not remove expert/raw access where it is genuinely useful.
- Do not put business logic only in JavaScript when the authoritative rule belongs in Core/store/runtime.
- Do not make the Hub depend on Internet access for normal operation.

## Acceptance criteria for every feature

A StageCore feature is not operator-complete unless:

1. its common path can be completed without scripts/raw JSON/manual database edits;
2. the UI states clearly what is happening and what the next safe action is;
3. validation/errors are understandable and actionable;
4. permissions and SHOW lock remain enforced server-side;
5. expert details are optional rather than required;
6. the workflow is keyboard/touch accessible as applicable;
7. the workflow can be localized and mirrored RTL without changing domain contracts;
8. automated tests cover authoritative state transitions and no UI shortcut bypasses those rules;
9. unsupported or unavailable capabilities are not presented as working actions.

## Definition of complete

F-002 should not be checked complete merely because the foundation exists. It remains a cross-cutting acceptance rule until the implemented StageCore operator workflows have compliant simple paths and the major raw-configuration gaps have visual alternatives.
