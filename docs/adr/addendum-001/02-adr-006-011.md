# **ADR-006 — StageCore Vault / Project Vault**

**Status:** Approved Design Direction

**Decision:** يوسع StageCore Media Management إلى **Project Vault / Show Archive** يحفظ ما يكفي لفهم العرض وإعادة بنائه مستقبلًا.

يمكن أن يضم Vault: Project Configuration، Cues، Routing، Notes، Rehearsal History، Show Sessions، Scripts، Plugin Manifests، Technical Fiche، Device Mappings، Machine Roles، Media، Documents، Production Notes، Runtime Snapshots وReports.

**Architectural implications:**

- Project Vault مكوّن منطقي له Manifest وهوية وإصدار وسياسات اكتمال، وليس مجرد Folder غير منظم.
- يجب التمييز بين محتوى مملوك للـVault ومراجع خارجية وفق ADR-007.
- يرتبط Vault بالـBackup والArchive Lifecycle والتحقق من سلامة البيانات.
- يجب أن تبقى Credentials منفصلة أوتحفظ بطريقة آمنة لا تكشفها عملية Archive/Export العادية.

**Open Questions:** Packaging Format، سياسات Retention، Deduplication، وقابلية نقل Vault بين إصدارات StageCore.

# **ADR-007 — Managed Media vs Referenced Media**

**Status:** Approved Design Direction

**Decision:** يدعم كل Media Asset واحدة من سياسات الحفظ التالية بدل إجبار المستخدم على نسخ كل الملفات إلى الـHub.

- **Reference Only:** يحتفظ StageCore بالمرجع والـMetadata بينما يوجد الملف على جهاز أوStorage خارجي.
- **Managed by StageCore:** ينسخ Master File إلى Project Vault.
- **Archive Required:** يجب أن توجد نسخة داخل الأرشيف قبل اعتبار المشروع Archive Complete.

**Architectural implications:**

- يسجل Asset Policy، Source Location، Content Identity، Availability وحالة Archive.
- يكشف StageCore الملفات المستخدمة فعليًا في Cues وغير المؤرشفة.
- لا تعني Reference Only أن الملف صالح للعرض؛ Runtime Sync وPreflight يحددان الجاهزية.
- تغيير السياسة أوالمصدر عملية موثقة ولا يغير Cues التي تشير إلى Asset Identity.

**Open Questions:** السياسة الافتراضية عند Import، معالجة تراخيص المحتوى، وقواعد Portable External Storage.

# **ADR-008 — Runtime Media Cache**

**Status:** Approved Design Direction

**Decision:** يمكن أن يكون Hub هو Master Repository، لكن Live Video Playback لا يعتمد افتراضيًا على Streaming منه. تتم مزامنة الوسائط المطلوبة إلى Local SSD على Mac/PC قبل العرض، ثم يشغلها Playback Software محليًا.

**Architectural implications:**

- يولد StageCore Required Media List لكل Machine Role.
- تستخدم عملية Sync Checksums وVersion Verification وMissing File Detection.
- يعرض Preflight اكتمالًا واضحًا مثل VIDEO-MAIN: 47 / 47 synchronized.
- لا يحذف Cache صالح أثناء Show Mode، ولا يستهلك Sync الثقيل مسار P1.
- يمكن دعم Streaming مستقبلًا كخيار Capability-specific، لا كافتراض معماري عام.

**Open Questions:** Cache Eviction، حجز المساحة، حدود Bandwidth، وزمن التهيئة المقبول قبل العرض.

# **ADR-009 — Media Version Integrity**

**Status:** Approved Design Direction

**Decision:** تعتمد هوية الوسائط على Checksum / Content Identity وليس Filename وحده.

يجب أن يحدد StageCore هل تغير الملف، أي نسخة استُخدمت في Show محدد، هل Local Cache يطابق Master، وهل النسخة المؤرشفة كاملة. ترتبط Show Runtime Snapshot بنسخ Media التي استخدمت فعليًا.

**Architectural implications:**

- Filename وPath Metadata وليسا هوية موثوقة للمحتوى.
- يميز النظام بين Same Content/Different Location وSame Name/Different Content.
- يسجل Sync Manifest وVerification Result ووقت الفحص.
- تغيير Master بعد Publish يولد Version Mismatch ولا يحدث Runtime Snapshot بصمت.

**Open Questions:** خوارزمية Content Identity، التعامل مع الملفات الضخمة، ووقت إعادة الفحص عند تغير Metadata فقط.

# **ADR-010 — Runtime Snapshot & Publish to Show**

**Status:** Approved Design Direction

**Decision:** تعديلات EDIT MODE لا تصبح حالة عرض معتمدة مباشرة. يستخدم StageCore **Publish to Show** لإنشاء **Show Runtime Snapshot** مرقم وغير ملتبس، مثل Al-Omyaan — Runtime v17.

يوزع الـSnapshot أوManifest الخاص به على Companions وNodes وOperator Clients. قبل العرض ينفذ **SYNC CHECK** يقارن الإصدار المتوقع على جميع الأطراف ويظهر أي جهاز متأخر.

**Architectural implications:**

- يفصل Draft Configuration عن Published Runtime State بصورة قابلة للتدقيق.
- Snapshot يثبت Project Version وRole Assignments وMappings وPlugin/Media requirements ذات الصلة.
- لا يغير Publish الحالة الفيزيائية للأجهزة تلقائيًا؛ بل يجهز Runtime معتمدًا.
- يجب أن يكون Rollback إلى Snapshot سابق صريحًا ومؤهلًا بالسلامة.

**Open Questions:** Emergency Patch أثناء Show، قواعد Snapshot Immutability، ومن يملك صلاحية Publish/Rollback.

# **ADR-011 — Limited Runtime Resilience**

**Status:** Approved Design Direction

**Decision:** يحتفظ Companion وNodes بـRuntime Cache محدود لدعم استمرارية محلية محسوبة عند انقطاع قصير، دون أن يتحولا إلى Hub مستقل.

قد يتضمن Cache: Current Published Configuration، Local Mappings، Required Local Commands، Current Project Identity وEmergency/Fallback Behavior محدود.

**Architectural implications:**

- تحدد كل Capability سلوك Network Loss: hold أوsafe-off أوlocal-rule أوoperator decision.
- يرتبط Fallback بـSafety Classification وTTL وإصدار Snapshot.
- عند عودة الاتصال، يبلغ الطرف عن الأحداث المنفذة وحالته قبل استعادة القيادة الكاملة.
- لا تعني Reconnection إعادة تنفيذ آخر Command تلقائيًا.

**Open Questions:** مصفوفة Fallback التفصيلية، مدة Offline المسموحة، وسياسة Conflict Resolution بعد Reconnect.
