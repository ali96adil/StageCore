# **ADR-018 — Backup Architecture**

**Status:** Approved Design Direction

**Decision:** يعتمد StageCore أربع طبقات حماية مستقلة ومتكاملة.

- **Level 1 — Local Protection:** Autosave، Database Snapshots، Configuration History وFast Rollback؛ ليس Backup خارجيًا.
- **Level 2 — Project Backup:** نسخة كاملة لمشروع محدد وVault Metadata/Content وفق السياسة.
- **Level 3 — Full StageCore Backup:** Projects، Registry، Plugins/Configuration، Users/Roles، Machine Roles، Settings، Secrets الآمنة وVault Metadata.
- **Level 4 — System Recovery:** StageCore Version، OS/Runtime Requirements، Database Schema، Plugin Versions، Configuration وRestore Procedure لإعادة البناء على Hub جديد.

**Architectural implications:** لكل مستوى Scope وManifest وRetention وRestore Procedure. لا يعلن نجاح الحماية قبل إمكانية التحقق والاستعادة.

**Open Questions:** RPO/RTO لكل مستوى، Consistency أثناء النسخ، وكيفية تصدير Secrets دون كسر نموذج الأمان.

# **ADR-019 — Backup Destinations**

**Status:** Approved Design Direction

**Decision:** يسمح التصميم مستقبلًا بالنسخ إلى Local External SSD وNAS وNetwork Storage وEncrypted Cloud Backup.

يمكن استخدام Incremental Backup وDeduplication وChecksums وEncryption. Cloud قناة إدارة وحماية ولا يدخل في Live Show Critical Path.

**Architectural implications:**

- تعرف كل Destination بهوية وثقة وسعة وحالة وآخر نجاح/تحقق.
- تعزل Credentials عن Project Data وتدار بصلاحيات مناسبة.
- يتوقف أوينخفض Backup عند تعارضه مع P0/P1 أوShow Mode.
- فشل Destination لا يفسد Snapshot المحلي الصالح.

**Open Questions:** مزودات Cloud المدعومة، Key Custody، سياسة Dedup المشفرة، وحدود Bandwidth والتكلفة.

# **ADR-020 — Automatic Home / Trusted Network Backup**

**Status:** Approved Design Direction

**Decision:** يمكن تعريف **Trusted Backup Network** لتشغيل Backup تلقائي عندما يرى StageCore NAS أوDestination موثوقًا خارج Show Mode ومع استقرار الطاقة والشبكة.

القاعدة المرجعية: إذا لم يكن النظام في SHOW MODE، والـNAS متاح، والطاقة والشبكة مستقرتان، ينفذ Backup للمشاريع المعلقة.

**Architectural implications:**

- Network Presence وحده لا يثبت الثقة؛ تستخدم هوية Destination موثقة.
- Scheduler واعٍ بالوضع والأولوية والطاقة والسعة.
- يمكن Pause/Resume ويعرض Pending/Running/Verified/Failed بوضوح.
- لا يبدأ Backup ثقيل أثناء Show Mode، ويمكن إيقاف Management Work قبل الانتقال إليه.

**Open Questions:** تعريف Power Stable، جداول الانتظار، وسلوك الأجهزة المحمولة عند انقطاع الشبكة أثناء النسخ.

# **ADR-021 — Backup Verification**

**Status:** Approved Design Direction

**Decision:** لا تكفي حالة Backup Completed. يوفر StageCore **Verify Backup** لفحص Manifest وDatabase Integrity وChecksums وMedia Availability وArchive Completeness.

**Architectural implications:**

- يعرض النظام تاريخ آخر Backup وآخر Verify ونتيجتهما بصورة منفصلة.
- يسجل Verification Report بالأخطاء والنواقص ونسخة StageCore المطلوبة للاستعادة.
- يجب دعم Restore Test دوري أوعلى الأقل Sample Restore وفق مستوى الحماية.
- Backup غير متحقق لا يوصف للمستخدم بأنه Recovery Ready.

**Open Questions:** معدل Full Verify، عمق Sample Restore، وسياسة تنبيه المستخدم عند تقادم آخر تحقق.

# **ADR-022 — Storage Hardware Direction**

**Status:** Approved Design Direction

**Decision:** لا يعتمد Project Vault وMedia Archive وDatabase التشغيلية المهمة على microSD كوسيط تخزين أساسي طويل الأمد.

الاتجاه المستهدف: Raspberry Pi أوMini PC class للـCompute، وSSD/NVMe للتخزين الأساسي، بسعات مثل 1TB أو2TB حسب Product Tier. يمكن استخدام microSD للـBoot فقط إذا برر التصميم النهائي ذلك.

**Architectural implications:**

- يبقى القرار Hardware Independent ولا يختار Vendor أوModel نهائيًا.
- يجب مراقبة Storage Health والسعة ودرجة الحرارة وأخطاء I/O حيث تتوفر.
- يفصل التصميم بين Boot/Runtime Data/Vault/Backup Destinations منطقيًا حتى لو اجتمعت ماديًا في نسخة أولى.
- انخفاض السعة أوHealth يولد Warning/Blocker مناسب قبل فقد البيانات.

**Open Questions:** Product Tiers، Filesystem، Redundancy، Encryption at Rest، وحدود Wear/Endurance المطلوبة.
